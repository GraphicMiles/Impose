# Adversarial hardening audit

Date: 2026-09-18
Scope: live Supabase project, relay, gateway, database grants, every write
path in Community and Workspace.

## What was found and what was done

### P0 - direct signup bypassed the whole code flow (fixed live)

The project had `disable_signup = false` and `mailer_autoconfirm = true`.
Any browser holding the publishable key could call
`/auth/v1/signup` and receive a confirmed, fully usable session with no
email check, no password rule, and no spam filter. Every guard the relay
implements was optional: the front door was open beside it. This is how
the keyboard-mash accounts (`skskdjdjdjdh`, the repeated-letter one, the
flood accounts) reached the database.

Fixed through the management API and verified against the live project:

- `disable_signup = true` - accounts can only be created by the relay's
  service role, after a code delivered to the address is consumed.
- `mailer_autoconfirm = false` - if signup is ever opened again, a
  confirmation is still required.
- `password_min_length = 8` - matches the rule the product states.
- `security_update_password_require_reauthentication = true`.
- `site_url` / `uri_allow_list` moved from `http://localhost:3000` to the
  deployed site.

Live probe after the change: `POST /auth/v1/signup` answers 422
`signup_disabled`. The relay's signup path is unaffected because it
creates users with the service role, which this setting does not bind.

### P0 - TRUNCATE, REFERENCES, TRIGGER granted to anon and authenticated (fixed live)

Supabase's project defaults grant ALL on new tables to the API roles, and
the tables created in 0001-0004 predate the default-privilege revoke in
0005. Eleven tables carried the grants; only `notifications`, created
after 0005, did not. TRUNCATE is the one that matters: it does not
consult row level security, so it is one callable code path away from
wiping the community. No such path exists today (PostgREST does not serve
TRUNCATE), but a landmine is a landmine.

Fixed by migration 0013, applied and verified: the sweep revokes the
three privileges on every table, table level and column level, and the
schema tests pin the result plus the survival of the intended grants
(public reads, the lock/visibility/soft-delete column updates).

### P1 - cosmetic enforcement, now server side (0013 + relay)

- `update_my_profile` accepted any string: no length bound, no character
  rules, no spam check, and `profiles.display_name` had no constraint. A
  megabyte name or one built from control and zero-width characters
  stored fine and rendered on every card. Now: 2-40 characters after
  sanitising invisible characters, at least one letter or digit, no
  control characters, no spam shapes, plus a check constraint as the
  final gate. Every refusal is a named error the client words for a
  person.
- `join_waitlist` validated shape only. It now runs the same disposable
  domain list and spam-shape rules as signup, bounds address length, and
  caps table growth at 100000 rows (the table is anonymously writable by
  design, so unbounded insert is a slow way to spend project storage).
- The signup trigger copied the raw email local part into
  `display_name`. It now sanitises and caps it, because the trigger
  serves every path that can create a user, not just the relay.
- The relay refuses signup addresses whose local part is keyboard mash:
  five of a character in a row, a two or three character block repeated
  three times, or six letters with no vowel. Reset keeps the shape rules
  only, so a legacy address can still recover.
- The relay no longer mails codes for password resets on unknown
  addresses. Issuing anyway made the endpoint a mail relay for arbitrary
  inboxes. The answer is identical to the known-address case, so the
  change adds no enumeration channel.
- `create_generation` and `create_comment` name their size refusals
  (`prompt_length`, `response_length`, `body_length`) instead of letting
  the constraint speak.
- The `X-Request-Id` echo strips control characters before the header and
  the log: an echoed request header is a classic injection point.
- The Lightning gateway's key check had no failure budget, the exact gap
  the relay already documented and fixed. It now rate-limits failed key
  attempts per IP, same shape as the relay.

The spam-shape rules live three times on purpose (relay, database
`text_is_spammy`, browser): one per trust boundary, identical logic, so a
string any boundary refuses is refused by all of them. The browser copy
is fast feedback; the other two are the decision.

### Verified against the live project

- Direct table access with the publishable key: `auth_codes`,
  `auth_tickets`, `waitlist`, `workspace_grants` all answer 401; direct
  inserts into `generations` answer 401.
- Privileged RPCs (`issue_auth_code`, `consume_auth_code`,
  `redeem_auth_ticket`, `purge_*`, `rate_hit`) all answer 401 for anon
  and authenticated.
- `update_my_profile` refuses each reported shape over the wire and keeps
  ordinary names; zero-width characters are stripped, not stored.
- `join_waitlist` refuses mash, disposables and over-long addresses and
  still joins ordinary ones.

### Regressions guarded

- Relay: 17 new tests in `test_auth_rules.py` and `test_auth_flow.py`
  pin the spam refusals, the reset no-op, and the signup-only scope of
  the quality rules.
- Schema: new sections in `schema_test.sql` pin the privilege sweep, the
  name and bio rules, the waitlist rules, and the write-size guards.
- Client: the `taste.js` window over `shape()` covers the whole function
  again; the service worker version and fingerprint moved with the
  shipped assets; the standalone build is current.

All suites green: pytest (147), agent suites (272), build check.

## Remaining risks, accepted

1. `supabase/apply.sh` applies only the first migration. That predates
   this audit and was left untouched: making it apply all twelve safely
   needs migration tracking, and 0013 was applied through the management
   API instead. Until the script grows a ledger, apply new migrations the
   way this one was.
2. The spam heuristics are mechanical. They stop patterns, not a person
   determined to type a plausible name; that is moderation's job, and the
   rules were kept narrow so a real name never costs a retry.
3. The GoTrue recovery endpoint still exists for existing users. It is
   rate limited per IP and now points at the real site, but the product
   path stays the relay's code flow.
